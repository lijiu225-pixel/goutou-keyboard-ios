# 截图 OCR 第二阶段：结果清理与消息归属

第一阶段把「截图 → 本机 OCR → 人工修正 → 复制 JSON」这条链路跑通了，但真机上暴露了三个问题：

1. **右侧绿色气泡的多条消息被标成「未确定」**，左侧白色气泡基本正确；
2. 状态栏时间、聊天标题、居中日期、通话记录「已取消」被当成普通聊天；
3. 表情被认成 `C`、`こ` 之类的杂字，直接拼进了正文。

这一阶段只解决这三件事。**没有**接键盘导入、没有调 AI、没有改九键 / 候选词 / 人物记忆。

## 一、归属判错的真正原因

第一阶段是拿 **Vision 的文字框**当气泡用的（「文字框贴左 = 对方」）。真机截图量出来的数字说明这条路走不通：

| | 左侧白气泡 | 右侧绿气泡 |
|---|---|---|
| 气泡边缘 | 左边缘 5 条全部是 **0.1354** | 右边缘 6 条全部是 **0.8646…0.8672** |
| 文字框边缘 | 左边缘随句子长短变（0.1742…） | 右边缘在 0.82 上下飘 |

也就是说：

* **气泡边缘**对所有同侧消息是同一个常数 —— 它才是「谁说的」的判据；
* **文字框**只是「这一行字的墨迹范围」：长句会把文字框撑到几乎和气泡一样宽，
  短句又只占气泡中间一小段，所以文字框的左右边缘在长句上必然失效。

真机上那两行最长的绿气泡，文字框左边缘（0.2031 / 0.2125）和左侧白气泡的文字左边缘（0.1742）
只差 0.03，于是 `leftRatio - rightRatio` 算出来只有 0.04～0.06，低于阈值 → 全部落进「未确定」。

**修法**：先扫出每一行文字**所在气泡**的左右边缘，再在气泡边缘上找两条「对齐轨道」
（右侧消息共用一条右边缘、左侧消息共用一条左边缘），贴在哪条轨道上就是哪一侧。
颜色（偏绿）只在「两边贴得一样近」这种僵局里当辅助；头像只在两侧都没贴上轨道时当辅助；
什么都判不出来的时候**还是标「未确定」**，不硬猜。

## 二、气泡是怎么扫出来的

`Shared/GoutouChatBubbleScanner.swift`（纯 Foundation，可在 CI 上单独编译测试）+
`ChatOCRService` 里的一小段 CoreGraphics 采样。

1. 把工作图降采样成几百像素宽的分析图（`analysisWidth = 384`，1 像素约 0.3% 宽度）；
2. 用「量化后取众数」估出画布底色（真机那张截图里底色占 62%）；
3. 对每一行文字，在它纵向范围内取 5 个采样行，把「离底色明显不是同一个颜色」的列取**并集** ——
   并集是为了补掉文字笔画和 JPEG 压缩造成的小洞；
4. 取包含文字中心的那一段作为气泡，同时看同一批采样行里气泡左右两侧还有没有宽度像头像的色块。

用**底色**而不是「绿色」当判据，所以深色模式、白色气泡、自定义主题走的是同一条路：
浅色画布 236 与白气泡 255 的距离是 0.122，深色画布 17 与对方气泡 44 的距离是 0.183，
阈值取 0.06，两边都有 2 倍以上余量，而画布自身的噪声只有 0.01 上下。

扫不出气泡时（例如整张图都是纯色、或者气泡色和底色几乎一样）**退回第一阶段的老口径**，
不会因为没有气泡证据就乱判。

## 三、聊天区域过滤

顶部 / 底部不是按固定像素裁的，而是按**内容边界**推的：

* 有气泡证据的那些行的纵向范围 = 真实聊天区（band）；
* 完全落在 band 上方 → 状态栏时间、聊天标题、返回/更多按钮 → 直接剔掉；
* 完全落在 band 下方 → 输入框、工具条、可见键盘 → 直接剔掉；
* 截图被裁到只剩中间一段时，第一条消息就是 band 的顶，上方什么都不会被误剔。

所以：**长图分片时不会在每一片重复裁掉顶部和底部**（band 是整图算的），
裁剪过的截图也不会被凭空砍掉内容。

居中的日期时间、系统提示、通话记录**不删**，只标成「非聊天候选」：
默认不写进剪贴板，界面上单独一栏列出来，用户一键就能放回。

* 日期时间要同时满足「居中 + 没有气泡 + 文字结构像日期/时间」，
  所以聊天里真的出现的「明天21:56」「我们21:56见」不会被误伤（它们有气泡、也不居中）；
* 通话记录（`已取消` / `通话时长 00:12` …）只认**整条恰好是这些短语**，
  不做包含匹配，「他说已取消」不会中招。微信的通话记录本身也有绿气泡，所以这一条确实
  分不到 100% 准 —— 因此它只会成为「候选」，由用户决定，而不是被静默删掉。
* 键盘：一行里挤着 5 个以上小方块、连着两行以上、都在下半屏 → 整体判成键盘剔掉。
  真实聊天不可能长成这样。

## 四、表情乱码

表情被认成 `C`、`こ` 之类杂字时，**不自动改正文**，只给建议：

* 条件一：这一行的置信度本来就低（Vision 自己也没把握，真机上那两行正是这样）；
* 条件二：正文至少有 2 个汉字；
* 条件三：首/尾有一个**孤立**的单字符，且它不是汉字（ASCII 字母数字、假名、少数符号）。

界面上标「末尾像是表情被认错了」+ 一个「去掉末尾杂字」按钮，
批量菜单里也有一次清完的入口。**只有用户点了才会改文字**。

表情本身没有被识别出来（整条消息只有一个表情）的情况，这一阶段**不生成**「表情未识别」占位消息
—— 那需要把整张图的气泡做二维分割，留到以后。用户看到的是少了一条消息，而不是一条乱码。

## 五、保留的东西

* 图片只在本机处理，不落盘、不上传、不新增文件；
* 长图分片、坐标换算、重叠去重全部保留（顺手修了一个真实 bug，见下）；
* 清空 / 换图 / 退出时的任务取消与结果失效不变；
* 用户仍然可以改文字、改归属、删消息；复制仍然只由用户主动触发；
* 严格 JSON 契约、体量上限、**未确定不许进剪贴板**都不变；
* 不恢复 App Group，不调 AI，不自动插入，不自动发送；
* 不打印完整聊天、图片、剪贴板内容或密钥。

### 顺手修掉的坐标 bug

`ChatOCRCoordinateMapper.normalizedBox(fromWorkingNormalized:)` 原来乘的是 `1 / scale`，
但工作图和原图都是**相对自己边长的归一化**，均匀缩放下这个系数应该是 1。

后果：任何被降采样、又走了「单次识别」的普通截图（例如 1290×2796 缩到高 2400），
整张图的内容都会被放大到右下角，贴边的框直接跑出 0…1。
现在单次识别也走 `map(lines:tileOrigin: .zero)`（和分片同一条换算路径），
并加了 scale ≠ 1 的回归断言。

## 六、测试

* **纯逻辑**（`tools/ChatLayoutCheck`，不需要模拟器 / Vision）：
  气泡扫描（浅色 / 深色 / 头像 / 缝隙合并）、对齐轨道（只有一侧 / 两边一样贴 / 被裁到边缘）、
  聊天区域过滤、日期与系统提示的正反例、表情杂字建议、坐标换算回归。
  另外有一组**匿名化**的真实版式 fixture：坐标是从真机那张截图上量出来的，
  **文字换成了占位内容**，用来锁住「右侧长句判成未确定」这个具体毛病。
* **真 Vision**（`tools/ChatVisionCheck`，只在 macOS runner 上跑）：
  现场用 CoreGraphics 画一张匿名聊天截图（浅色 + 深色两版），
  交给和 App 完全同一套 `ChatOCRService` + `ChatLayoutParser`，
  断言页眉页脚被剔、归属判对、候选默认不复制。

合成坐标过了不等于 OCR 过了，所以这两步刻意分成两个 CI step。
私人聊天截图和完整聊天原文**不进仓库、不进 Actions artifact**。
