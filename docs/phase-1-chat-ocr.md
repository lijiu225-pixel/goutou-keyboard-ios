# 第一阶段：聊天截图 OCR → 剪贴板

> 本文只描述**当前实现**。早期「App Group 共享缓存」路线已废弃（购买的签名服务无法定制
> App Group），相关代码、状态行和两份 entitlement 已全部删除，历史记录见 git 提交
> `1a9ab62`。现在 App 与键盘之间**只有剪贴板**这一条通道。

本阶段**只做到「复制聊天 JSON」为止**：

```
用户主动选截图
  → 主 App 本机 Vision OCR（不保存图片、不上传、不联网）
  → 整理消息 + 初步判断归属（判不出来标「未确定」）
  → 用户改文字 / 改归属 / 删无关行
  → 用户主动点「复制聊天文字」写出带 format/version 标记的 JSON
```

键盘侧的「导入识别聊天」**还没有做**，AI 分析也不会读这份 JSON：主 App 的文案里不能
指引用户去点一个不存在的入口。下一阶段才接键盘导入、AI 分析和回复插入。

## 文件

| 文件 | 职责 |
| --- | --- |
| `Shared/GoutouChatClipboard.swift` | 剪贴板契约（`format`/`version`/`messages`）与编解码。App 写、键盘读，**同一份实现**。所有体量上限和 version 严格校验都在这里。 |
| `Shared/GoutouChatOCRGeometry.swift` | 长图分片的纯几何：缩放口径、切片计划、分片坐标换算回原图归一化、重叠文字去重。只依赖 Foundation，可单独编译测试。 |
| `App/ChatOCRService.swift` | 唯一碰截图的地方：`VNRecognizeTextRequest`（`.accurate`，简体中文 + 英文）+ 按计划裁片识别。图片只在内存里过一遍。 |
| `App/ChatLayoutParser.swift` | 把 OCR 散行按阅读顺序整理成消息，并按左右边缘间隙、宽度占比判断归属（**不是** `midX < 0.5`）。 |
| `App/ChatOCRView.swift` | 界面：`PhotosPicker` 选图、可编辑结果、复制。识别任务带请求标识，清空/换图/退出后旧结果一律作废。 |
| `tools/ChatLayoutCheck/main.swift` | 上面四份纯逻辑的冒烟测试（CI 上 `swiftc` 直接跑，不需要模拟器）。 |

## 长截图的支持范围与限制

整图把最长边压到 2400 像素时，1290×12000 的长截图宽度只剩 258 像素，聊天文字会糊到
认不出来。现在的口径：

1. 先按「最长边不超过 2400 像素」算缩放；
2. **如果这样算出来的宽度低于 480 像素，就退回按最小宽度定比例**（宁可片多一点，也不把文字压糊）；
3. 高度仍超过 2400 像素时竖着切 1400 像素高的片，**一次只渲染并识别一片**（峰值内存 ≈ 一片）；
4. 每片的 Vision 结果换算回**原图归一化坐标**（左上原点，0...1），和单次识别的口径完全一致；
5. 分片重叠区的重复文字按「同文本 + 纵向重叠 + 横向中心对齐」合并，保留置信度更高 / 文字更全的那条。

支持范围（`ChatOCRTilingConfig` 的默认值就是范围定义）：

- 原图像素总数 ≤ 6400 万（例如 1290 宽、约 49600 高）；
- 分片数 ≤ 60。1290 宽的长截图会先缩到工作图 645 宽，再切成 1400 像素高的片，
  所以实际支持到约 **83000 像素高**（60 片 × 1400 ÷ 0.5）；再高就明确报错。
- 缩放到可识别尺寸后宽度仍 ≥ 480 像素。

超出范围时**明确报错**，不静默缩到不可用：

- 像素太多 → 「这张图太大了，本机内存放不下…」
- 片数超限 → 「这张图有 N 像素高，需要切成 M 片，超过本阶段支持的上限…」
- 太窄 → 「这张图只有 N 像素宽，缩到能识别的尺寸后文字会糊…」

已知限制：

- **取消的粒度是「片」**：`VNImageRequestHandler.perform` 是同步阻塞调用，中途打断不了。
  取消后最多再白跑完当前这一片；界面侧靠请求标识保证旧结果不再更新。
- 重叠区同一行如果两片认出的文字**互不包含**（例如各错一个字），两条都会留下，需要用户手动删一条。
- 上下紧挨、横向中心几乎重合的两条不同消息，有被误判成重复的可能性（判据已经收窄到「文本互相包含」）。

## 剪贴板契约

```json
{"format":"goutou-chat","messages":[{"role":"me","text":"你好啊"},{"role":"other","text":"你好"}],"version":1}
```

- `role` 只认 `me` / `other`；界面上的「未确定」**不允许**写进剪贴板，复制前必须先定下来。
- `version` 必须是**数值类型的整数**：字符串、小数（`1.5`）、布尔（`true`）、`null`、超出双精度
  整数范围的数值一律拒绝（旧实现用 `NSNumber.intValue`，会把 `1.5` 截成 `1`、把 `true` 当成 `1`）。
- 已知版本 `1` 正常接受；未来的整数版本给出「不支持版本」提示。
- 体量上限集中在 `GoutouChatClipboardCodec`：200 条 / 单条 2000 字 / 整段 JSON 350 万字符。
  解码**在 `JSONSerialization` 之前**先卡总长度，避免巨大剪贴板内容在格式校验前耗尽内存；
  编码和解码共用同一套上限，不会出现「写得出来、读不回去」。
- 不打印聊天内容；错误文案只说第几条出了什么问题。

## CI 验证

```sh
# 纯逻辑（不需要模拟器 / 不需要 Xcode）
swiftc -swift-version 5 \
  Shared/GoutouChatClipboard.swift \
  App/ChatLayoutParser.swift \
  Shared/GoutouChatOCRGeometry.swift \
  tools/ChatLayoutCheck/main.swift -o /tmp/chatlayoutcheck
/tmp/chatlayoutcheck

# Swift 源码括号自检（粗查，不是编译验证；CI 上的真把关是 swiftc）
python tools/check-swift-braces.py
```

`/tmp/chatlayoutcheck` 覆盖不到、**必须真机**的部分：Vision 的识别质量、`PhotosPicker`、
SwiftUI 界面、以及取消行为在真实设备上的手感。

## 真机验收（尚未执行）

1. 装好后进主 App →「识别聊天截图」→ 选一张普通竖屏聊天截图，确认文字、归属、「未确定」标记。
2. 选一张长截图，确认文字仍可读、消息条数正常、没有整段重复。
3. 识别过程中点「取消」/ 直接退出页面 / 立刻换一张图，确认没有旧结果回填、也没有弹「识别失败」。
4. 改几条归属和文字，点「复制聊天文字」，确认剪贴板里是上述 JSON；
   **键盘侧的导入入口还不存在**，不要去找它。
5. 回归九键拼音、候选词、英文数字符号、删除、换行、军师面板与记忆管理。
